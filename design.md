# DESIGN.md --- Rinku Diwakar Website Design System & Experience Rules {#designmd--rinku-diwakar-website-design-system--experience-rules}

## 1. Design North Star {#1-design-north-star}

The website is a:

> **Living Builder\'s Journal**

It combines:

``` text
Editorial
+
Developer
+
Cinematic
```

The visual result should feel:

-   human;
-   warm;
-   technical;
-   confident;
-   spacious;
-   intentional;
-   modern without chasing trends.

It should not feel like:

-   a generic portfolio template;
-   a SaaS landing page;
-   a gaming interface;
-   a crypto dashboard;
-   a futuristic AI demo;
-   a resume builder;
-   a literal operating system.

------------------------------------------------------------------------

# 2. Normal Mode {#2-normal-mode}

Normal Mode is the default.

It is the primary experience for:

-   recruiters;
-   businesses;
-   curious visitors;
-   collaborators;
-   people discovering Rinku through search.

Visual language:

-   warm/light editorial foundation;
-   strong typography;
-   large but controlled display text;
-   readable body typography;
-   restrained blue accents;
-   subtle technical metadata;
-   clean composition;
-   generous whitespace;
-   personal photography.

------------------------------------------------------------------------

# 3. Developer Mode {#3-developer-mode}

Developer Mode is an alternate interpretation of the same identity.

Visual language:

-   dark;
-   macOS-inspired;
-   workspace/terminal;
-   monospaced accents;
-   restrained;
-   professional.

It should represent:

``` text
Rinku
as
code
```

not:

``` text
website
as
code
```

------------------------------------------------------------------------

# 4. Navigation {#4-navigation}

Preferred desktop structure:

``` text
RINKU
NOW
WORK
STORY
THINKING
ABOUT
CONTACT
⌘K
DEV
```

Navigation may be refined visually, but it must remain concise.

Do not fill the header with every route.

------------------------------------------------------------------------

# 5. Hero Design {#5-hero-design}

The hero must communicate within seconds:

``` text
WHO
WHAT
NOW
```

Use:

-   strong headline;
-   supporting sentence;
-   current-focus signal;
-   integrated portrait;
-   restrained technical annotation;
-   one or two clear actions.

Avoid:

-   huge circular profile photo;
-   "Hi I\'m Rinku" as the main idea;
-   résumé statistics;
-   logo soup.

The hero should feel like the opening page of a story.

------------------------------------------------------------------------

# 6. Story Composition {#6-story-composition}

The page should breathe.

Use:

-   large section transitions;
-   editorial rhythm;
-   occasional full-width moments;
-   narrow readable text columns;
-   technical annotations where meaningful;
-   visual changes to mark chapters.

Do not cardify every paragraph.

------------------------------------------------------------------------

# 7. Typography {#7-typography}

Use two primary typographic roles:

### Display

For:

-   hero;
-   chapter titles;
-   major statements.

Should feel editorial and distinctive.

### Body

For:

-   story;
-   case studies;
-   explanations.

Should prioritize readability.

### Monospace

Use selectively for:

-   status;
-   metadata;
-   code;
-   labels;
-   Developer Mode;
-   timestamps;
-   technical annotations.

Normal Mode must not become entirely monospaced.

------------------------------------------------------------------------

# 8. Color {#8-color}

Base:

``` text
warm / light
```

Accent:

``` text
restrained blue
```

System/product moments:

``` text
dark sections where useful
```

Developer Mode:

``` text
dark
```

Avoid:

-   neon;
-   rainbow gradients;
-   excessive gradients;
-   high-saturation UI;
-   gaming palettes.

Exact tokens belong to implementation.

------------------------------------------------------------------------

# 9. Spacing {#9-spacing}

The design should use generous vertical rhythm.

Large sections should feel distinct.

Prefer:

``` text
large whitespace
+
clear hierarchy
```

over:

``` text
dense information packing
```

The site should never feel like a dashboard full of widgets.

------------------------------------------------------------------------

# 10. Cards {#10-cards}

Cards exist to support:

-   grouping;
-   comparison;
-   navigation;
-   state.

Do not put every piece of text into a card.

Project cards should feel like story invitations, not résumé tiles.

------------------------------------------------------------------------

# 11. Buttons {#11-buttons}

Primary buttons:

-   obvious;
-   solid visual hierarchy;
-   accessible;
-   touch friendly.

Secondary buttons:

-   quieter;
-   still discoverable.

Required states:

``` text
default
hover
focus
pressed
disabled where applicable
```

------------------------------------------------------------------------

# 12. Photography {#12-photography}

Photography should feel personal and editorial.

The main portrait:

-   integrates into composition;
-   is not a generic profile circle;
-   uses intentional crops;
-   has meaningful alt text;
-   supports the story.

Do not use decorative stock images just to fill empty space.

------------------------------------------------------------------------

# 13. Homepage Sequence {#13-homepage-sequence}

Maintain:

``` text
00 Arrival
01 Hero
02 Now
03 Origin
04 Journey
05 First Build / Kavach
06 Things I've Built
07 What Building Taught Me
08 Pradrix
09 Build Log
10 Signals
11 Proof
12 Future
13 Epilogue
```

------------------------------------------------------------------------

# 14. Origin {#14-origin}

Visual idea:

> It didn\'t start with technology. It started with curiosity.

Keep it human.

Do not rewrite the story into:

> "I\'ve always loved technology."

That is not the intended narrative.

------------------------------------------------------------------------

# 15. Journey {#15-journey}

Desktop:

``` text
CURIOUS → EXPLORING → ENGINEERING → BUILDING → PRADRIX
```

Mobile:

``` text
CURIOUS
↓
EXPLORING
↓
ENGINEERING
↓
BUILDING
↓
PRADRIX
```

Interaction should reveal progression, not act as decoration.

------------------------------------------------------------------------

# 16. Kavach Visual Direction {#16-kavach-visual-direction}

Kavach is the signature cinematic moment.

Show a visual progression:

``` text
idea
→ assembly
→ system
→ test
→ failure
→ debugging
→ recovery
→ working
```

Use:

-   diagrams;
-   physical/hardware references;
-   system connections;
-   state labels;
-   restrained animation.

Do not turn it into a fake technical simulator.

------------------------------------------------------------------------

# 17. Pradrix Visual Direction {#17-pradrix-visual-direction}

Pradrix is the product climax.

Workflow:

``` text
UNDERSTAND
↓
FIND BOTTLENECK
↓
IS AI APPROPRIATE?
↓
DESIGN
↓
BUILD
↓
TEST
↓
DEPLOY
↓
MEASURE
```

The design should shift subtly toward:

``` text
system
+
workflow
+
product
```

while remaining consistent with the rest of the site.

Never use fake client logos or fake case studies.

------------------------------------------------------------------------

# 18. Build Log {#18-build-log}

Build Log should feel like a journal.

Use:

-   date;
-   title;
-   category;
-   concise update;
-   optional source.

Avoid:

``` text
Version 1.0.0
Version 1.0.1
Version 1.0.2
```

unless that is genuinely how the work evolved.

------------------------------------------------------------------------

# 19. Signals {#19-signals}

Signals answer:

> What is Rinku doing lately?

Show a curated, meaningful selection.

Do not create a social-media wall.

If nothing reliable exists:

> Nothing new here yet. The work continues elsewhere.

------------------------------------------------------------------------

# 20. Proof {#20-proof}

Proof should be visible but secondary.

Use:

-   source labels;
-   verification indicators;
-   View source;
-   contextual links.

Avoid footnote-heavy academic styling.

------------------------------------------------------------------------

# 21. Future {#21-future}

Future should feel open.

Communicate:

-   desire to build;
-   technical growth;
-   product thinking;
-   entrepreneurship;
-   meaningful problems;
-   Pradrix as current chapter.

Do not invent a fixed ten-year job title.

------------------------------------------------------------------------

# 22. Epilogue {#22-epilogue}

End simply:

> **The story isn\'t finished.**

Then:

> **Maybe you can be part of the next chapter.**

Connection paths:

``` text
Work With Me
Build With Me
Talk To Me
```

The ending should feel like the natural conclusion of the story, not a
sales banner.

------------------------------------------------------------------------

# 23. Motion {#23-motion}

Only three major cinematic moments:

1.  Hero typography transition.
2.  Kavach build/failure/debug sequence.
3.  Pradrix workflow transition.

Everything else should be restrained:

-   fade;
-   reveal;
-   slight translation;
-   hover;
-   state transition.

Never use motion to hide content.

------------------------------------------------------------------------

# 24. Reduced Motion {#24-reduced-motion}

When reduced motion is enabled:

-   preserve the full story;
-   remove or simplify cinematic transitions;
-   preserve state information;
-   preserve navigation;
-   preserve interactions.

A visitor should never feel like they received a broken version of the
site.

------------------------------------------------------------------------

# 25. Mobile Design {#25-mobile-design}

Mobile is a first-class composition.

Use:

``` text
horizontal timeline → vertical timeline
multi-column → stacked
complex architecture → stacked/swipeable
command palette → bottom sheet
cinematic motion → simplified
developer workspace → touch-friendly panels
```

Do not rely on:

-   hover;
-   precise cursor interactions;
-   tiny controls;
-   keyboard shortcuts.

------------------------------------------------------------------------

# 26. Responsive Typography {#26-responsive-typography}

Typography must scale intentionally.

Do not simply shrink desktop headings.

Maintain:

-   readable line lengths;
-   comfortable line height;
-   strong hierarchy;
-   adequate spacing.

------------------------------------------------------------------------

# 27. Developer Mode Layout {#27-developer-mode-layout}

Desktop can use:

``` text
┌─────────────────────────────────────────────┐
│ top bar                                     │
├──────────────┬──────────────────────────────┤
│ file tree    │ editor / content             │
│              │                              │
│              ├──────────────────────────────┤
│              │ terminal                     │
└──────────────┴──────────────────────────────┘
```

Mobile:

``` text
top bar
↓
file/content panel
↓
terminal panel
```

Panels must remain usable by touch and keyboard.

------------------------------------------------------------------------

# 28. Interaction Principle {#28-interaction-principle}

Every interaction must do at least one:

1.  tell the story;
2.  demonstrate capability;
3.  reveal personality;
4.  provide evidence;
5.  help navigation.

If it does none of these, remove it.

------------------------------------------------------------------------

# 29. Visual Restraint {#29-visual-restraint}

Use one strong visual idea at a time.

Do not stack:

``` text
parallax
+
blur
+
3D
+
particles
+
scroll hijacking
+
terminal
```

just because they are technically possible.

The experience should feel designed, not overloaded.

------------------------------------------------------------------------

# 30. Recruiter Experience {#30-recruiter-experience}

A recruiter must quickly find:

``` text
Identity
→ Work
→ Experience / Resume
→ Proof
→ Contact
```

Do not force recruiters through Developer Mode.

Do not hide the résumé.

------------------------------------------------------------------------

# 31. Developer Experience {#31-developer-experience}

A technical visitor should quickly reach:

``` text
Work
→ Case Study
→ Architecture
→ GitHub
→ Developer Mode
```

Developer Mode is a reward for curiosity, not a gate.

------------------------------------------------------------------------

# 32. Business Experience {#32-business-experience}

A business visitor should quickly reach:

``` text
Pradrix
→ Problem
→ Approach
→ Example workflow
→ Current stage
→ Contact
```

Pradrix should not look like a generic AI-agency website.

------------------------------------------------------------------------

# 33. Final Design Test {#33-final-design-test}

Open the site with no explanation.

Within five seconds:

> Who is Rinku?

Within thirty seconds:

> What does he build?

Within one minute:

> What is he building now?

Within several minutes:

> Why does he build?

And after exploring:

> I understand this person and I want to know what he builds next.
